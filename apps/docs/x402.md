# x402 Agentic Payments

Vellar lets a smart account pay [x402](https://x402.org) (HTTP-402) resources —
the **"give your agent a budget, not your keys"** flow. An autonomous agent holds
a scoped session key that can pay for x402-protected APIs on its own, but only
within a budget **enforced on-chain** by a spending-limit policy. The agent never
holds the account's admin key, and it physically cannot spend beyond its cap.

> Status: **implemented in the SDK** (`vellar-sdk` ≥ 0.4.0) and proven on testnet.
> The web UI for minting/revoking agent session keys is planned (see
> [Roadmap](#roadmap)).

## What x402 is

x402 is an open payment protocol built on HTTP 402 "Payment Required". A resource
server answers an unpaid request with `402` plus **payment requirements** (amount,
asset, recipient, network). The client builds a signed payment and retries; a
hosted **facilitator** verifies and settles it on-chain. On Stellar, the payment
is a SEP-41 token transfer authorized by a Soroban authorization entry.

## How Vellar pays

Vellar pays as a **smart account** (a C-address), not a classic keypair. The
`vellar-sdk` x402 client handles the whole exchange:

```
GET /paid ──▶ 402 + requirements
           ◀──
build SEP-41 transfer(from = smart account, to = payTo, amount)
   │
   ▼ sign the wallet auth entry (V1 credentials) with the session key
   │
   ▼ retry with the PAYMENT-SIGNATURE header
           ──▶ facilitator verifies (re-simulates → runs the wallet's
               __check_auth, which runs the budget policy) → settles on-chain
           ◀── 200 + the unlocked resource + settlement (tx hash)
```

Because the facilitator verifies by **re-simulation**, the account's on-chain
budget policy runs at verify time — so an over-budget or wrong-token payment is
rejected *before* it ever settles.

## Quick start (SDK)

x402 lives on the wallet handle as `wallet.x402`. Configure it with a **signer**
(who pays) and a `simulationSourceAccount` (any funded classic account, used only
to simulate — the facilitator rebuilds the transaction and pays the network fee):

```ts
import { createVellarWallet, createSessionKeySigner } from "vellar-sdk";

const vellar = createVellarWallet({
  /* …network, appName, kit, backend, sac, isValidAddress… */
  x402: {
    // Agent flow: a scoped ed25519 session key signs headlessly (no passkey).
    signer: createSessionKeySigner({
      address: walletCAddress, // the smart account that pays
      secretKey: sessionKeySecret, // the session key attached to it
    }),
    simulationSourceAccount: aFundedGAccount,
  },
});

const { response, paid, settlement } = await vellar.x402.fetch(
  "https://api.example.com/paid",
  {
    maxAmount: 1_000_000n, // hard per-request ceiling, in the asset's base units
    // allowedAssets: [usdcSac], // optional — restrict which asset(s) you'll pay in
  },
);

if (paid) console.log("settled on-chain:", settlement.transaction);
const data = await response.json(); // the unlocked resource
```

## The two signers

Both satisfy the same `SmartAccountX402Signer` interface, so the client is
signer-agnostic:

| Signer | Flow | Prompt? |
| ------ | ---- | ------- |
| `createSessionKeySigner({ address, secretKey })` | **Agent** — a scoped ed25519 session key signs headlessly. Its authority is bounded on-chain by the spending-limit policy attached to it. | None (the whole point — an agent runs unattended). |
| `createPasskeyX402Signer({ address, webAuthn })` | **Human** — a person pays an x402 resource from the web app. `webAuthn` is a seam you wire to your passkey ceremony. | One passkey prompt per payment. |

Both produce **V1 (`sorobanCredentialsAddress`) credentials** in the smart-wallet
signature format the account's `__check_auth` expects. (The SDK builds this
itself rather than delegating to passkey-kit, which unconditionally upgrades to
V2 credentials that hosted facilitators reject.)

## The budget is on-chain — `maxAmount` is only a guard

There are **two independent protections**, and it matters that they are different:

- **`maxAmount` (client-side):** the SDK refuses to *sign* a payment whose
  required amount exceeds the ceiling you pass. It guards against an
  over-charging or misconfigured server — but it is only as trustworthy as the
  client process. **It is not the budget.**
- **The spending-limit policy (on-chain):** the real, enforced budget. The agent
  session key is attached to the account with `SignerLimits` that require a
  **spending-limit policy** to co-sign any transfer. That policy caps cumulative
  spend over a rolling window, evaluated inside `__check_auth` at settlement time.
  Even if client code is bypassed entirely, the chain refuses to move funds
  beyond the cap.

Use the **token-scoped** spending-limit policy for an agent budget so that only
one specific token's transfers count against it (a generic spending-limit policy
sums every SEP-41 transfer into one bucket — see
[Policy Contract](./policy-contract.md)). "Give your agent $10/day of USDC" then
means exactly that: USDC only, capped, on-chain.

## Facilitators and the fee ceiling

The exact scheme requires **sponsored fees** — the facilitator rebuilds the
transaction with its own source account and pays the Stellar fee, so the smart
account needs no XLM. The SDK rejects a payment option that does not advertise
sponsored fees.

A **policy-governed** payment runs the spending-limit policy inside
`__check_auth`, which costs more resource fee than a plain transfer. Hosted
facilitators cap the fee they will sponsor (the reference `x402.org` facilitator
defaults to 50,000 stroops), which a policy-governed payment can exceed. Such a
payment needs a facilitator configured with a higher ceiling — self-hosted, or a
hosted one that allows it. A plain (non-policy) transfer stays well under the
default.

## Errors

The client throws typed errors so callers can react precisely:

| Error | When |
| ----- | ---- |
| `MaxAmountExceededError` | The server asked for more than your `maxAmount`. Nothing was signed. |
| `DisallowedAssetError` | No offered asset was in your `allowedAssets`. Nothing was signed. |
| `NoUsablePaymentOptionError` | No offered option matched the scheme/network, or none sponsored fees. |
| `InvalidRequirementsError` | A requirement was malformed (e.g. a non-integer amount). |
| `PaymentRejectedError` | The facilitator rejected the payment at verify — e.g. an over-budget payment blocked by the on-chain policy. Carries the facilitator's reason. |
| `X402NotConfiguredError` | `wallet.x402` was used without `x402` config. |

## Security model

- **No key custody, bounded delegation.** The agent holds a scoped session key,
  never the account's admin passkey. The human grants the budget once (attaching
  the session key + policy with a passkey signature); autonomous spends within
  that grant are pre-authorized bounded delegation, not silent signing of the
  account. Anything outside the grant still requires the passkey.
- **Honest budgets.** The enforced on-chain behavior is exactly what the UI
  states — a cumulative rolling-window allowance, per token. Budgets are enforced
  by the policy contract on-chain, not by client code.
- **Testnet-first.** Mainnet agent budgets are gated on the smart-contract
  security review (see [Security Model](./security-model.md)).
